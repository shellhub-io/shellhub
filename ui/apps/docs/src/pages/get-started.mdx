# Onboarding Guide

The short path from nothing to a terminal on a device. Three steps, plus an account to do them
with.

## 0. Get an account and a namespace

A namespace is what devices join and what your team shares. Its name is part of every address
you use to reach a device, so it is worth a moment: short, lowercase, no dots.

<Tabs items={["Cloud", "Self-hosted", "Invited"]}>
<Fragment slot="cloud">

[Sign up](https://cloud.shellhub.io/sign-up) with a name, a username, an email and a password,
then click the link that arrives by email. Until you do, signing in returns you to the
confirmation screen.

Signing up creates the account and not the namespace. The first time you sign in the console
asks for one, and holds there until it has it — there is nothing else to reach without a
namespace.

<Shot id="create-namespace" route="/devices" account="no-namespace" of={{ testId: "create-namespace" }} frame="band" alt="The screen that asks a new account to name its first namespace" />

Type a name and you land on an empty dashboard, as the owner of it.

</Fragment>
<Fragment slot="self-hosted">

Bring the server up with the [Self-Hosting Quickstart](/selfhosted/quickstart). Until the first
account exists every path on it redirects to `/setup`, which asks for the account and the
namespace on one screen and creates both together.

That first account is the instance's superadmin, and on Community its namespace is *the*
namespace — the server refuses to create a second. See [Editions](/about/editions).

Then use your own address wherever the rest of this page says `cloud.shellhub.io`.

</Fragment>
<Fragment slot="invited">

The invitation is the account. Open the link, set a password, and you are in a namespace
somebody else owns, with whatever role they gave you.

Nothing to create, so skip to step 1 — or straight to step 3, if there are devices in there
already. What you are allowed to do with them is a matter of that role and of the namespace's
access policies; see [User Roles](/manage/team/user-roles).

</Fragment>
</Tabs>

## 1. Install the agent

The console builds the command for you. **Devices** → **Add Device** asks two things: whether
this is one machine or a fleet, and how the agent should be installed.

<Shot id="add-device" route="/devices/add" of={{ role: "main" }} alt="The Add Device screen, with the audience and install method chosen and the command it built" />

Copy what it gives you and run it on the device you want to reach. For one machine on a host
with Docker, Podman, or systemd, that is:

```bash
$ curl -sSf https://cloud.shellhub.io/install.sh | sh
```

The script is served by the server it registers with, which renders the address into it on the
way out, so there is nothing to point at anything.

Left on **Auto Detect** the installer inspects the machine and picks: Docker, then Podman, then
Snap, then WSL, then a native binary under systemd. To choose yourself, or to know what it
picked, see [Choosing a Method](/get-started/install).

Leave it on **One device** for now. **Fleet** is the same screen with an install key baked into
the command, and it changes what happens in step 2 — that is the path to take once one device
works.

<Callout variant="info">
Fetch the script from your own server and the agent registers there instead —
`curl -sSf https://shellhub.example.com/install.sh | sh`. `SERVER_ADDRESS` overrides that,
and is only needed when the two differ. See [Enrolling Devices](/get-started/enrolling-devices).
</Callout>

## 2. Accept the device

Give the agent nothing and it pairs. The installer finishes by asking the server for a code,
printing it, and waiting:

```
To accept this device, open the ShellHub console and enter this code:

      4KQP-7M2X

Enter it at https://cloud.shellhub.io/accept-device, or open the link:

  https://cloud.shellhub.io/accept-device?code=4KQP7M2X

Waiting for acceptance... (code expires in 10 minutes)
```

On a machine with a desktop the browser opens by itself. On a server, open the link from
wherever you are, or type the code into the console.

Either way the same page opens. It shows what the device reported about itself — hostname,
operating system, MAC address — and asks which namespace it joins. Check that it is the machine
you think it is, then accept.

<Shot id="accept-device" route="/accept-device?code=:paircode" of={{ testId: "login-card" }} frame="band" alt="The accept page for a paired device, showing what it reported about itself and the namespace it will join" />

The agent is still waiting on the device. Accepting ends that wait: it joins the namespace,
connects, and there is no second command to run.

The code lives ten minutes, and a device has one at a time — asking for another invalidates the
last. If it expires before you get to it:

```bash
$ sudo shellhub-agent login    # native install
$ shellhub-agent login         # container install
```

For a machine nobody is standing at, an [install key](/manage/devices/install-keys) replaces this
step entirely: the key's mode decides, so a fleet arrives accepted and tagged instead of asking.

## 3. Connect

Open the device in the console and click the terminal button. That is the whole flow — no client
to install, no key to arrange.

<Shot id="device-connect" route="/devices" of={{ role: "dialog" }} before={[{ click: { role: "button", name: "Connect" } }]} alt="The Connect panel for a device, with the ways to open a session on it" />

To use your own SSH client instead, the device's page carries its address, with a copy button:

```bash
$ ssh <username>@<namespace>.<device>@cloud.shellhub.io
```

<Shot id="device-details" route="/devices/:device" alt="Device details page showing the SSHID with a copy button" />

The first connection from a key ShellHub has not seen is parked for a member to approve, and
approving binds that key to your account for good — see
[Login Approvals](/manage/access-control/login-approvals).

## What to do next

Now that one device works, the questions that come up in order:

- **More devices, without accepting each one by hand** — [Install Keys](/manage/devices/install-keys)
- **Other people need access** — [Members](/manage/team), then [Access Policies](/manage/access-control/access-policies)
- **More than a shell** — [File Transfer](/connect/file-transfer), [Port Forwarding](/connect/port-forwarding), [Container Access](/connect/container-access)
- **Automation** — [API keys](/api#creating-a-key) and [Service Accounts](/manage/access-control/service-accounts)

<Callout variant="info">
A new namespace starts with one access policy, granting the owner every login on
every device. Everybody else starts with no access at all, which is deliberate — see
[How Authorization Works](/manage/access-control).
</Callout>
