# Automation access

An automation reaches devices as an API key. The key is the principal: it has a name, it can be
revoked, and it can expire. To connect over SSH it holds an SSH identity of its own, and where it
may reach is decided by an access policy naming it.

Use this for anything that connects without a person: a pipeline, a monitoring job, a deployment
runner.

## Why not a person's key

Because of what happens later.

A pipeline configured with an engineer's key works until that engineer leaves. Their identity is
revoked, and the pipeline breaks at the worst possible moment, with a cause nobody guesses
quickly.

Before that, every deploy in the audit trail is attributed to a person who was not deploying, so
the record actively misleads.

An API key fixes both. The trail says `ci-deploy`. Revoking a person touches nothing the
automation depends on.

## Giving a key a way in

Create the API key first, on the **Team** page under **API Keys**. Each key there has an **SSH
access** column saying what it can connect with. Open it, choose **Add SSH key**, and paste the
public key the automation will connect with.

A key's credentials live with the key, not on the **SSH Identities** page, which is about people.
That page shows your own and, for a manager, other members'; it never lists what an automation
holds.

Enrolling a key for an API key needs permission to manage SSH identities, which an administrator
and an owner hold. Adding your own key is not enough: opening a door for something else is a
different act.

## Granting access

An automation holds no membership and no role over SSH, so a policy has to name the key. This is
the part that trips people up.

**An `all-members` allow does not cover an automation.** It is not a member, so nothing written
about members reaches it, and neither does a policy naming a role.

| Name | Effect | Subject | Devices | Logins |
|---|---|---|---|---|
| Pipeline deploys | allow | API key `ci-deploy` | tag `production` | `deploy` |

An `all-members` **deny** does not cover it either. A namespace-wide "no root anywhere" has to
name the key, or be written as a deny naming it.

## Key lifecycle

Two limits worth using here more than anywhere else.

**Expiry.** Give the SSH key a deadline, so an automation nobody has touched in a year does not
still hold live credentials.

**Single use.** The key authorizes one established session and is then consumed. For a genuinely
one-shot job, a provisioning run or a migration, this is the tightest thing available.

Revoking the API key removes the SSH identities it owns and the policies naming it, in one act.
An expired API key opens nothing, even while its SSH key is still enrolled.

## No re-authentication

A policy's `require_reauth` never applies to an automation. Re-auth is an interactive browser
step and there is nobody to complete it, so demanding one would hang the connection.

Freshness here comes from the key's lifecycle, expiry and single use, not from a periodic prompt.
If a path needs re-auth, it needs a human on it.
