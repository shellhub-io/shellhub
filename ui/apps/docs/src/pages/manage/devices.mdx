# Managing Devices

Every machine running an agent appears under **Devices**.

## How a device enrols

Installing the agent is half of it. The other half is the device joining a namespace, and what
the agent was given at install decides both how it joins and whether anybody has to act on it.

| Given | Lands | Good for |
|---|---|---|
| Nothing | Accepted, once somebody opens the link it prints | A device in front of you |
| A [provisioning key](/manage/devices/provisioning-keys) | Whatever the key's mode says | Fleets, images, production |
| A tenant ID | Pending, for review | Deprecated; what a [legacy namespace](/manage/access-control/migrating-from-legacy) accepts |

Given nothing, the agent pairs: it asks the server for a code, prints it with a link, and waits
for somebody to accept it in the browser. That is the path the
[Quickstart](/get-started) walks, and the one to use for a machine you are standing at.

A provisioning key is the answer at any volume. It names the namespace on its own and its mode
decides acceptance, so a fleet arrives accepted and tagged instead of arriving as a queue.

A tenant ID also names the namespace, and is how a legacy namespace enrolls every device: it
always leaves the device pending, in the queue behind the namespace's built-in key. A new namespace
still accepts it the same way, but it is deprecated, so nothing new should use it.

## Statuses

| Status | Meaning |
|---|---|
| `accepted` | In the namespace and reachable |
| `pending` | Enrolled, waiting to be accepted. Cannot be connected to |
| `rejected` | Explicitly refused |
| `removed` | Deleted from the namespace |
| `unused` | Registered but never used |

Only accepted devices can be connected to. A device sitting in pending is not broken — it is
waiting for somebody, on the activity of the key it enrolled with — see
[Provisioning Keys](/manage/devices/provisioning-keys#reviewing-a-pending-enrollment).

## Online and offline

Separate from status. A device is online while its agent holds a connection to the server, and
offline when it does not.

The agent sends a keepalive every 30 seconds by default and reconnects on its own, waiting a
random 5 to 65 seconds before each attempt, so a brief network problem resolves itself without anybody doing anything. A device
that stays offline has a real cause — see
[Device Not Appearing](/manage/devices/device-not-appearing).

## What identifies a device

The agent's **private key**, at `SHELLHUB_PRIVATE_KEY`, together with the identity it reports. The
identity is the MAC address, or `SHELLHUB_PREFERRED_IDENTITY` when set. Not the hostname, not the
IP. The identity also decides whether accepting a new device replaces an old one, covered in
[Replacing an offline device](#replacing-an-offline-device).

The consequences are worth internalizing:

- Rename the machine and it is the same device.
- Move it to another network and it is the same device.
- Lose the key with a reflash, a recreated container or a wiped volume, and it is a **new**
  device. The old entry stays behind, unless the new device reports the same identity and accepting it
  replaces the old one, as described below.

Most confusing device lists are the result of that last one.

## Replacing an offline device

A device also reports an identity, which is its MAC address, or the value of
`SHELLHUB_PREFERRED_IDENTITY` when the agent sets it. The server does not verify it.

When a pending device is accepted and an accepted device in the namespace reports the same
identity and is offline, the new device replaces the old one. It takes the old device's name and
session history, and the server deletes the old entry with its tags and custom fields. This is how
a reflashed machine keeps its name and history. It also means a device that claims another device's
identity takes over its name, and `ssh user@namespace.name` reaches the new machine from then on.

Who can make that happen:

- **Accepting by hand, or accepting a pairing code**, replaces a device only for a member allowed
  to remove devices. An operator gets a refusal and the old device stays. The console names the
  device an accept replaces before you confirm. Through the API, the accept must also send
  `"replace": true`, or it is refused with a 409 naming the device it would replace.
- **A provisioning key** replaces by default. Turn off **Replace offline devices** on a key you do
  not trust with that, and its devices wait in **Pending** instead.
- **An old device that is connected** is never replaced. The accept is refused until its agent
  stops.

The device's page shows the device it replaced and when. The provisioning key's history lists every
replacement as an entry of its own, and keeps it after the old entry is gone.

## Names

A device's name defaults to its hostname and is what you type in an SSHID:

```bash
$ ssh root@mycompany.raspberrypi@cloud.shellhub.io
```

You can rename a device in the console. Set `SHELLHUB_PREFERRED_HOSTNAME` on the agent when the
system hostname is not meaningful — a container with a random name, or a fleet where every unit
reports the same one.

Names matter beyond typing: the legacy public key ACL and firewall rules can select devices by a
hostname pattern, so a naming convention is something you can write rules against there. Access
policies select by tag instead — see [Tags](/manage/devices/tags).

## Details

Opening a device shows its SSHID with a copy button, plus what the agent reports about it — OS,
architecture, agent version, when it was last seen.

The agent version is the first thing to check when something behaves oddly on one device and not
another.

## Rejecting and removing

**Rejected** refuses the device and keeps the record, so the refusal is still visible later.
**Removed** deletes it from the namespace.

Neither stops the agent. If it is still running with the same key and configuration, it
re-enrolls — and depending on how it enrolls, may come straight back.

To retire a device properly: stop the agent on it, *then* remove it here.
