# Sessions

Every connection through ShellHub is a session, and every session is recorded in the list —
whether or not the *contents* were recorded.

<Shot id="session-list" route="/sessions" of={{ role: "main" }} alt="The Sessions page listing active and historical SSH sessions" />

## What a session tells you

| | |
|---|---|
| Who | The authenticated principal — a person or a service account |
| Which device | |
| Which unix login | The user they connected as |
| When | Start, and end for a closed session |
| From where | The client address, resolved through `SHELLHUB_PROXY_TRUSTED_IPS` |

That "who" is the payoff of the identity model. In the legacy model the record could only name the
key that was used; here it names the principal the key belongs to. See
[How Authorization Works](/manage/access-control).

### A red username is worth stopping on

A username shown in red, with a warning triangle, marks a session that **never
authenticated**. A record is written when a connection arrives and flipped to authenticated
only once the SSH authentication succeeds, so a red row is an attempt that reached the server
and got no further.

One is ordinary — a wrong key, a client that gave up. A run of them against one device, or
from one address, is the thing this list exists to show you.

## Session details

Active sessions can be inspected while they run. A session with a recording has a play control.

## Sessions and authorization

Worth understanding together, because it explains something that otherwise looks like a bug.

**Authorization happens once, when the connection is made.** Revoking an identity, deleting a
policy or removing a member does not end a session already running. It was authorized when it
started, and it continues until it is closed.

So the sessions list is not only history — for live sessions it is the answer to "who is connected
right now", and the place to look after revoking somebody's access if you need to be sure they are
actually gone.

## Recording

ShellHub can capture what happened in a terminal and play it back. There are **two** recording
mechanisms, and they are genuinely different — mixing them up is the most common misunderstanding
here.

| | Browser-local | Server-side |
|---|---|---|
| Edition | **Community**, Cloud, Enterprise | Cloud and Enterprise |
| Where the recording lives | In the browser that opened the session | On the server |
| Covers | Web terminal sessions from that browser | Every session, including native SSH clients |
| Survives clearing site data | No | Yes |
| Available to other members | No | Yes |

**Browser-local recording is in Community.** The web terminal records the session in the browser
and keeps it there. It is real and useful for reviewing your own work, and it is not an audit
trail: it is on one machine, it belongs to one person, and it disappears with the browser's site
data.

**Server-side recording is Cloud and Enterprise.** It is made by the server, so it covers sessions
from any client, is stored centrally, and is available to anyone with permission. That is the one
that satisfies a compliance requirement. Turn it on in [Settings](/manage/settings); it applies to
new sessions, and sessions already running are unaffected.

So "does Community have session recording" has an honest answer of "yes, but probably not the kind
you mean".

### Playing one

From the session's detail page, which replays the terminal in real time — what was typed, what was
displayed, and the timing between them.

<Shot id="session-player" route="/sessions/:session" of={{ role: "dialog" }} before={[{ click: { role: "button", name: "Play Recording" } }]} alt="A recorded session replaying, with the terminal and the playback controls" />

One consequence worth knowing: **a local recording plays without the `session:play` permission**,
because it is your own browser data rather than something the server holds. Server-side playback
is permission-gated as you would expect.

### What a recording holds

**Captured:** everything the terminal displayed, everything typed, and terminal resizes.

**Not captured:** file transfer payloads, and forwarded port traffic. A recording will show
somebody ran `scp`; it will not show the file's contents. It will show they opened a forward; it
will not show what went through it.

Know that before relying on recordings for an audit requirement.

### Deciding what gets recorded

A recording is a replay of a terminal, so it holds whatever that terminal showed. Two controls
decide how much of that exists and who reaches it.

**Recording is a namespace setting, and it is off until you turn it on.** Turn it off and the
server records nothing from then on. Nothing obliges a namespace to record, and a namespace that
does not need an audit trail should not.

**Playback is administrator and owner only.** An operator can open a session and read the session
list, and still cannot replay one. A recording is not something everybody in the namespace can
watch — see [User Roles](/manage/team/user-roles).

## What is not here

**Denial reasons.** A refused connection does not become a session — it was refused before the
device was contacted. The reason is not surfaced to the client either. See
[Connection Denied](/manage/access-control/connection-denied).

**Web endpoint traffic.** A [web endpoint](/connect/web-endpoints) is reached by URL, not by an
authenticated session, so requests to it do not appear here.
