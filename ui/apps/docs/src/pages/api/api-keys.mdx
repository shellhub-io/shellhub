# API Keys

An API key is a namespace-scoped credential for the REST API. It is what a script, a pipeline or
an integration should hold.

## Creating one

From the console. A key has:

| Field | Meaning |
|---|---|
| **Name** | Unique within the namespace. How you identify it later |
| **Role** | `administrator`, `operator`, or `observer` |
| **Expiry** | Optional. A key with no expiry never expires |

The name is the only external identifier — the key's internal id is a hash and is never returned.
So name keys for what they do: `ci-deploy`, `inventory-sync`, not `key1`.

## Roles

An API key carries a role and is subject to the same permission checks as a user holding it. See
[User Roles](/manage/team/user-roles).

<Callout variant="warning">
A key's role must be **equal to or less than the role of whoever created it**. An
operator cannot mint an administrator key. That constraint is what stops key creation from being
a privilege escalation path.
</Callout>

Give a key the least role that does the job. Most integrations read; an observer key is enough,
and an observer key that leaks is a much smaller problem.

## Expiry

Expiry is optional, and a key without one is valid until revoked.

Set one anyway where you can. A key with a deadline is a key that stops mattering on its own if
somebody forgets it exists — and forgotten credentials are the ones that turn up in a repository
two years later.

## What API keys cannot do

Some routes refuse API keys regardless of role:

- Namespace membership operations
- Install key management
- MFA
- User management

Structural, not a permission. If your automation needs one of these, it needs a human.

## API keys are not SSH identities

The distinction matters and it catches people.

| | API key | SSH identity |
|---|---|---|
| Used for | The REST API and MCP | SSH connections |
| Looks like | A token in a header | A public key |
| Governed by | Roles and permissions | [Access policies](/manage/access-control/access-policies) |

**An API key cannot open an SSH session, and an SSH identity cannot call the API.** Automation
that does both needs both: an API key for the REST calls, and a
[service account](/manage/access-control/service-accounts) holding an SSH identity for the
connections.

## Rotating

Create the new key, move consumers to it, then delete the old one. Name them so you can tell which
is which mid-rotation — `ci-deploy-2026` rather than editing in place.

Deleting takes effect immediately. Anything still using it starts getting `401`.
