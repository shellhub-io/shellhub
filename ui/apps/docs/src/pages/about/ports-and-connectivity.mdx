# Ports and Connectivity

This page exists so you can answer the network team's questions in one go.

## On the device

**Outbound access to the ShellHub server's HTTP(S) address. That is the whole requirement.**

The agent dials the address you gave it in `SHELLHUB_SERVER_ADDRESS` and holds that connection
open. It does not listen. Nothing has to be forwarded to it, published for it, or arranged in
advance.

That means all of the following are fine, with no configuration:

- Behind NAT, including carrier-grade NAT with no public address at all
- Behind a corporate firewall that only permits outbound web traffic
- Behind an HTTP proxy
- On a mobile or satellite link
- On a network you do not administer, such as a customer's

If a browser on that device could load a web page from your server, the agent can connect.

<Callout variant="info">
ShellHub does not require the device to be reachable, but the **server** does have to
be. That is the asymmetry the whole design rests on: one reachable server, any number of
unreachable devices.
</Callout>

## On the server

| Port | Variable | Default | What for |
|---|---|---|---|
| HTTP | `SHELLHUB_HTTP_PORT` | `80` | Web console, API, and the agents' connections |
| HTTPS | `SHELLHUB_HTTPS_PORT` | `443` | The same, with TLS. **Only bound when `SHELLHUB_AUTO_SSL=true`** |
| SSH | `SHELLHUB_SSH_PORT` | `22` | Native SSH clients |

Two details that surprise people:

**The HTTPS port is not bound unless auto-SSL is on.** The port mapping lives in an overlay that
is only applied when `SHELLHUB_AUTO_SSL=true`. If you terminate TLS somewhere else, you are
publishing HTTP and your proxy is doing the rest. List that proxy in `SHELLHUB_PROXY_TRUSTED_IPS`,
as [Behind a load balancer or reverse proxy](/about/ports-and-connectivity#behind-a-load-balancer-or-reverse-proxy) explains, or
every client appears at its address.

**SSH does not go through the gateway.** The SSH port is published by the server process
directly. The gateway handles web traffic only. If you are putting a load balancer in front of
ShellHub, the SSH port needs its own path — it is not HTTP and it will not survive an HTTP proxy.

## Behind a load balancer or reverse proxy

A Layer 4 load balancer can pass the client address in a PROXY protocol header. The gateway and
the SSH port read that header under separate settings.

For web traffic, set `SHELLHUB_PROXY=true` on the gateway and list your balancer's ranges in
`SHELLHUB_PROXY_TRUSTED_IPS`. The server refuses to start with one and not the other. Only those
ranges may declare a client address.

An HTTP reverse proxy such as nginx, Caddy or Traefik names the client in `X-Forwarded-For`
instead. Leave `SHELLHUB_PROXY` off and list the proxy's ranges in `SHELLHUB_PROXY_TRUSTED_IPS`.
ShellHub reads `X-Forwarded-For` from right to left, skips every address in those ranges, and takes
the first address outside them as the client. A client outside the ranges can add entries on the
left, but it cannot change the ones your proxies append. A peer outside the ranges is its own client, whatever its
headers say. ShellHub does not read `X-Real-IP`, so a proxy that sets only `X-Real-IP` makes every
client appear at the proxy's address. Configure it to append to `X-Forwarded-For`.

List only your proxies. ShellHub treats every address in a listed range as a proxy, so a host inside
one can name any client address it likes in `X-Forwarded-For`. A broad range such as `10.0.0.0/8`
that also holds your users lets each of them choose the address that lockout, firewall rules and
access policies see.

Without the gateway (`SHELLHUB_GATEWAY=false`), port `8080` applies the same rule with the same
`SHELLHUB_PROXY_TRUSTED_IPS`, and also trusts loopback. List your ingress or load balancer there.

For SSH, set `SHELLHUB_SSH_PROXY_TRUSTED_IPS` to the space-separated ranges the header arrives
from, such as your balancer's or your ingress pods'. The SSH port always trusts loopback and
nothing else by default. It closes a connection whose header comes from any other peer, and logs
a warning with that peer's address. Under Docker Compose, do not list the Docker bridge range:
every external client appears to come from it.

This matters beyond cosmetics: access policy source IPs, firewall rules and the session audit trail
read the client address of SSH and web terminal sessions, and password lockout reads it at web
sign-in. Get it wrong and all of them operate on the balancer's address.

## TLS

Three ways to get a certificate:

**Automatic.** Set `SHELLHUB_AUTO_SSL=true` and `SHELLHUB_DOMAIN` to a name that resolves to the
server. Certificates are obtained from Let's Encrypt and renewed for you. This requires the
server to be reachable for the challenge.

**Your own certificate.** Set `SHELLHUB_TLS_CERT_FILE` and `SHELLHUB_TLS_KEY_FILE` to paths
inside the server container. Set **both**: with only one, the server will not start.

**Terminate elsewhere.** Leave auto-SSL off, publish HTTP, and let your existing proxy or load
balancer hold the certificate. List it in `SHELLHUB_PROXY_TRUSTED_IPS` as
[Behind a load balancer or reverse proxy](/about/ports-and-connectivity#behind-a-load-balancer-or-reverse-proxy) explains.

`SHELLHUB_ACME_CA_SERVER` points at a different ACME directory if you are using an internal CA.
Empty means Let's Encrypt production.
