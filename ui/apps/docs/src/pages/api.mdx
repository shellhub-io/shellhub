# REST API

ShellHub exposes a REST API. [API Reference](/api/reference) is every route it has; this page is
how you get in and what a credential can do once you are.

## Authenticating

Two credentials work, and they are for different things.

An **API key** goes in a header:

```bash
$ curl -H "X-API-Key: <your-api-key>" https://cloud.shellhub.io/api/devices
```

It resolves to an identity carrying a namespace and a role. It belongs to the namespace rather
than to a browser session, and its expiry is one you set at creation rather than a session lifetime
the server imposes.

A **bearer token** is the JWT from signing in:

```bash
$ curl -H "Authorization: Bearer <token>" https://cloud.shellhub.io/api/devices
```

Tokens come in two kinds: a user token, from a person signing in, and a device token, which an
agent uses. For user tokens the role is re-read from the store on every request rather than
trusted from the token, so a role change takes effect immediately.

**Anything unattended should hold an API key.** A script driving a bearer token has to handle
sign-in and expiry, and if it does that with a person's credentials it breaks the day that person
leaves.

## Creating a key

From the console, under **Team → API Keys**. A key has:

| Field | Meaning |
|---|---|
| **Name** | Unique within the namespace. How you identify it later |
| **Role** | `administrator`, `operator`, or `observer` |
| **Expiry** | Optional. A key with no expiry never expires |

The name is the only external identifier — the internal id is a hash and is never returned. Name
keys for what they do: `ci-deploy`, `inventory-sync`, not `key1`.

A key is scoped to the one namespace it was created in. It reaches nothing in another namespace,
and it is not accepted on the instance administration surface under `/admin/api`, which takes a
credential of its own.

<Callout variant="warning">
A key's role must be **equal to or less than the role of whoever created it**. An operator cannot
mint an administrator key. That constraint is what stops key creation from being a privilege
escalation path.
</Callout>

Give a key the least role that does the job, and set an expiry where you can. Most integrations
only read, an observer key is enough, and a key with a deadline stops mattering on its own if
somebody forgets it exists. See [User Roles](/manage/team/user-roles).

## What a key cannot do

Some routes refuse API keys regardless of role:

- Namespace membership operations
- Install key management
- MFA
- User management

These are human-only flows. The refusal is structural, not a permission you can grant.

## A key is not an SSH identity

The distinction catches people.

| | API key | SSH identity |
|---|---|---|
| Used for | The REST API and MCP | SSH connections |
| Looks like | A token in a header | A public key |
| Governed by | Roles and permissions | [Access policies](/manage/access-control/access-policies) |

**An API key cannot open an SSH session, and an SSH identity cannot call the API.** Automation
doing both needs both: a key for the REST calls, and a
[service account](/manage/access-control/service-accounts) holding an SSH identity for the
connections.

## Rotating a key

Create the new key, move consumers to it, then delete the old one. Name them so you can tell them
apart mid-rotation — `ci-deploy-2026` rather than editing in place. Deleting takes effect
immediately, and anything still using the old key starts getting `401`.

## When a credential is refused

An unresolvable credential produces no identity rather than an error, so a protected route answers
`401` — the same answer whether the key does not exist, has expired, or was never valid. The API
does not tell an unauthenticated caller which of those it was.

So a `401` means "this credential is not usable", not "this credential does not exist".

## Paginating a response

List endpoints take `page` and `per_page`:

```bash
$ curl -H "X-API-KEY: $KEY" \
    "https://cloud.shellhub.io/api/devices?page=1&per_page=100"
```

## The specification

[API Reference](/api/reference) renders it in the browser. The files are the same thing, to diff
or to hand to a generator:

| Edition | Specification |
|---|---|
| **Community** | [community-openapi.yaml](/openapi/community-openapi.yaml) |
| **Cloud** | [cloud-openapi.yaml](/openapi/cloud-openapi.yaml) |
| **Enterprise** | [enterprise-openapi.yaml](/openapi/enterprise-openapi.yaml) |

**Take the one matching your edition.** Editions expose different routes: a Community server has
no MFA, firewall rule, or web endpoint routes at all, so a client generated from the wrong file
produces methods that answer 404. That is not a permission problem — the route is not there. See
[Editions](/about/editions).
