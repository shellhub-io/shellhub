# API Authentication

ShellHub exposes a REST API. Two credentials get you in, and they behave differently.

## API key

A header:

```bash
$ curl -H "X-API-Key: <your-api-key>" https://cloud.shellhub.io/api/devices
```

An API key resolves to an identity carrying a tenant and a role. It is the credential for
automation — it does not expire on a timer, and it belongs to a namespace rather than a browser
session.

See [API Keys](/api/api-keys).

## Bearer token

A JWT from signing in:

```bash
$ curl -H "Authorization: Bearer <token>" https://cloud.shellhub.io/api/devices
```

Tokens come in two kinds: a **user** token, from a person signing in, and a **device** token,
which an agent uses.

For user tokens, the role and admin flag are re-fetched from the store on **every request** rather
than trusted from the token. A role change takes effect immediately, without waiting for the token
to expire.

## Which to use

Anything unattended should hold an **API key**. A script driving a bearer token has to handle
sign-in and expiry, and if it does that with a person's credentials it breaks when that person
leaves.

## When a credential is not accepted

An unresolvable credential produces **no identity** rather than an error, so a protected route
answers `401` — the same answer whether the key does not exist, has expired, or was never valid.
That is deliberate: the API does not tell an unauthenticated caller which of those it was.

So a `401` means "this credential is not usable", not "this credential does not exist".

## Paginating a response

List endpoints take `page` and `per_page`:

```bash
$ curl -H "X-API-KEY: $KEY" \
    "https://cloud.shellhub.io/api/devices?page=1&per_page=100"
```

## What API keys cannot do

A number of routes refuse API keys outright, regardless of the key's role:

- Namespace membership operations
- Install key management
- MFA
- User management

These are human-only flows. The refusal is structural, not a permission you can grant.

## Roles apply

An API key carries a role, and it is subject to exactly the same permission checks a user with
that role would be. A key with the observer role can read and connect, and nothing else.

See [User Roles](/manage/team/user-roles).
