# Enrolling Devices

Installing the agent is half the job. The other half is the device joining a namespace and being
accepted into it. There are three ways that happens, and picking the wrong one is the usual reason
a device sits in **Pending** forever.

## The three ways

| Way | You provide | Device lands | Good for |
|---|---|---|---|
| **Pairing** | Nothing | Accepted, once you open the link | A device in front of you |
| **Install key** | `SHELLHUB_INSTALL_KEY` | Depends on the key's mode | Fleets, images, production |
| **Tenant ID** | `SHELLHUB_TENANT_ID` | Pending | <Deprecated /> |

Set one or the other. An install key identifies the namespace on its own; a tenant ID is the
older way of naming it, and it is on its way out.

### Pairing

The default. Give the agent nothing and it pairs: it generates its key, asks the server for a
code, and prints a link that carries it.

```bash
$ curl -sSf https://cloud.shellhub.io/install.sh | sh
```

Open the link and the console asks you to accept the device, showing its hostname, operating
system and MAC address so you can check it is the machine you think it is. Sign up on the way
through if you have no account, and pick the namespace if you have more than one.

The device ends up accepted rather than waiting in the pending list, and nothing else runs on it.

If the link does not appear — a slow first boot outruns the wait the script gives the agent to
write its key — ask for a new one:

```bash
$ sudo shellhub-agent login    # native install
$ shellhub-agent login         # container install
```

On a container install `shellhub-agent` is a wrapper on the host that execs into the container,
which is also how it manages to open your browser from inside one.

### Install key

The answer for anything at volume. An install key is a reusable credential you create once and
put in an image or a provisioning script.

```bash
$ curl -sSf https://cloud.shellhub.io/install.sh | INSTALL_KEY=<your-install-key> sh
```

The key applies its own tags and ephemeral flag to the device. What happens next depends on the
key's mode — automatic acceptance, manual review, a webhook, or a MAC allowlist. See
[Install Keys](/manage/devices/install-keys).

### Tenant ID

The original way: hand the agent your namespace identifier and it enrolls, landing on the
**Pending** tab for you to accept.

```bash
$ curl -sSf https://cloud.shellhub.io/install.sh | TENANT_ID=<your-tenant-id> sh
```

<Callout variant="warning" title="Do not build anything new on this">
Tenant-only enrollment is deprecated and will be removed. It always requires a manual
acceptance, which is fine for one device and unworkable for fifty, and it is the reason a
fleet arrives as a queue instead of as a fleet.

Pairing covers the single device with no tenant to paste. An install key covers everything
else, and decides acceptance for you. Neither leaves a queue behind.
</Callout>

## Choosing

- **One device, in front of you** — pairing. Run the line, open the link.
- **More than a handful, or an image** — install key, every time.
- **Anything else** — still one of those two.

## Device statuses

| Status | Meaning |
|---|---|
| `pending` | Enrolled, awaiting acceptance. Cannot be connected to |
| `accepted` | In the namespace and reachable |
| `rejected` | Explicitly refused |
| `removed` | Deleted from the namespace |
| `unused` | Registered but never used |
