# Install the Agent

The agent is what a device runs. It opens one outbound connection to the server and keeps it,
which is what makes the machine reachable without anything listening on it.

If you are setting up your first device, the [Quickstart](/get-started) walks the whole path.
This page is the reference for the install itself.

<ActionLink href="https://cloud.shellhub.io/install">Install ShellHub</ActionLink>

The script behind it is served by the server it will register with, which writes its own address
into it on the way out — port included. Fetch it from your own server and you get one that
registers there, with nothing to pass.

## Platforms

The installer picks one of these by looking at the machine, in this order: Docker, Podman, Snap,
WSL, then a native binary. Follow a page to see what the method leaves on the machine, or to run
it yourself.

- [Docker](/get-started/install/docker) — The agent in a container, on any host with a daemon.
- [Podman](/get-started/install/podman) — The same, without a daemon running as root.
- [Snap](/get-started/install/snap) — For Ubuntu and anything else carrying snapd.
- [Standalone Binary](/get-started/install/standalone) — A native binary under systemd, no
  container runtime.
- [WSL](/get-started/install/wsl) — Ubuntu under Windows Subsystem for Linux.

Architectures are detected: `amd64`, `armv6`, `armv7`, `arm64`, `386`.

## Additional platforms

The installer assumes a machine that already exists, with somebody — or a provisioning script —
running a command on it. These are not that command with a different flag.

Yocto and Buildroot are embedded build systems: the agent goes into the product image while the
image is being built, before there is a machine to run anything on, and whoever does it is
building the firmware rather than using it. FreeBSD has its own packaging. Building from source
is you producing the binary.

- [Raspberry Pi](/get-started/install/raspberry-pi) — A card image that enrols itself on first
  boot.
- [Yocto Project](/get-started/install/yocto) — The `meta-shellhub` OpenEmbedded layer, so the
  agent is in the image the build produces.
- [Buildroot](/get-started/install/buildroot) — The ShellHub external tree, same idea.
- [FreeBSD](/get-started/install/freebsd) — The
  [ShellHub ports tree](https://github.com/shellhub-io/ports).
- [Building from Source](/get-started/install/build-from-source) — For a platform nothing above
  covers, or to run an agent you built yourself.

Shipping the agent inside an image raises two questions that installing onto a machine never
does.

### How does a unit enrol with nobody there?

A unit coming off a line has no console to open and no link to click. The image carries an
[install key](/manage/devices/install-keys) instead: units enrol with it and are accepted as they
come online, tags already set. A tenant ID would leave the whole run pending for somebody to work
through by hand.

### Where does the device key come from?

A device is identified by a key the agent holds — not by its hostname, not by its MAC address.
The agent generates that key the first time it starts, if it does not already have one.

Which means the generation has to happen on the unit, not in the image:

- A key already **in the image** is the same key on every unit written from it. The whole run
  shows up as a single device that appears to move between machines.
- A key the unit **cannot keep** — storage that is read-only, or wiped on reboot — is generated
  again on every boot. One unit shows up as a new device each time it starts.

Which file holds it, and how to point the agent somewhere else, is in
[Agent Configuration](/get-started/agent-configuration).

## Uninstalling

Supported for standalone, WSL, Docker and Podman:

```bash
$ curl -sSf https://cloud.shellhub.io/install.sh | sh -s uninstall
```

Other methods will refuse rather than half-remove themselves. A Snap install is removed with
`snap remove shellhub`.

## The agent wrapper

Container installs also drop a `shellhub-agent` command on the host. It exists so
`shellhub-agent login` can open a browser during pairing — an agent inside a container cannot do
that on its own. See [Enrolling Devices](/get-started/enrolling-devices).
