# Install the Agent

The agent is what a device runs. It opens one outbound connection to the server and keeps it,
which is what makes the machine reachable without anything listening on it.

If you are setting up your first device, the [Quickstart](/get-started) walks the whole path.
This page is the reference for the install itself.

<ActionLink href="https://cloud.shellhub.io/install">Install ShellHub</ActionLink>

The script behind it is served by the server it will register with, which writes its own address
into it on the way out — port included. Fetch it from your own server and you get one that
registers there, with nothing to pass.

## Platforms

The installer picks one of these by looking at the machine, in this order: Docker, Podman, Snap,
WSL, then a native binary. Follow a page to see what the method leaves on the machine, or to run
it yourself.

- [Docker](/get-started/install/docker) — The agent in a container, on any host with a daemon.
- [Podman](/get-started/install/podman) — The same, without a daemon running as root.
- [Snap](/get-started/install/snap) — For Ubuntu and anything else carrying snapd.
- [Standalone Binary](/get-started/install/standalone) — A native binary under systemd, no
  container runtime.
- [WSL](/get-started/install/wsl) — Ubuntu under Windows Subsystem for Linux.

Architectures are detected: `amd64`, `armv6`, `armv7`, `arm64`, `386`.

## Additional platforms

These do not go through the installer at all. Each is a different route onto the machine, for
machines the one-liner cannot reach.

- [Raspberry Pi](/get-started/install/raspberry-pi) — The installer, then the device key removed
  before imaging the card.
- [Yocto Project](/get-started/install/yocto) — The `meta-shellhub` OpenEmbedded layer, baked into
  a product image.
- [Buildroot](/get-started/install/buildroot) — The ShellHub external tree, same idea.
- [FreeBSD](/get-started/install/freebsd) — The
  [ShellHub ports tree](https://github.com/shellhub-io/ports). The installer refuses FreeBSD
  deliberately.
- [Building from Source](/get-started/install/build-from-source) — For a platform nothing above
  covers, or to run an agent you built.

The first three build the agent into an image, which is a different problem from installing onto
a machine that already boots: there is no shell to pipe into at the point the decision is made.
Two things change with it, and both decide whether a production run arrives as a fleet or as a
problem.

**Enrollment has to happen with nobody present.** There is no console to open and no link to
click on a unit coming off a line, so the image carries an
[install key](/manage/devices/install-keys) and units are accepted as they come online, with
their tags already set. A tenant ID would leave the whole run pending.

**The device key must be absent from the image and writable on the device.** The agent generates
it when the file is missing. A key baked into the image gives every unit the same identity — one
device that appears to move between machines — and a key path that is read-only or volatile gives
a new device on every boot.

## Uninstalling

Supported for standalone, WSL, Docker and Podman:

```bash
$ curl -sSf https://cloud.shellhub.io/install.sh | sh -s uninstall
```

Other methods will refuse rather than half-remove themselves. A Snap install is removed with
`snap remove shellhub`.

## The agent wrapper

Container installs also drop a `shellhub-agent` command on the host. It exists so
`shellhub-agent login` can open a browser during pairing — an agent inside a container cannot do
that on its own. See [Enrolling Devices](/get-started/enrolling-devices).
